Published researchDec 2024 – May 2025first author of four

Dengue outbreak forecasting: dataset and model

A monthly 2015–2024 dataset for barangays in Koronadal City, South Cotabato, and a forecasting study built on it.

problem
Case counts, climate and geography were held by different agencies in formats that didn't agree on units, resolution or place names. There was no single table to model from.
my part
Sourcing, reconciliation, completeness and consistency checks, and the first-author write-up.
how
Merged DOH-CHD SOCCSKSARGEN case records, climate data (DOST PAG-ASA, Google Earth Engine rasters) and NAMRIA shapefiles, joined on location and month, into 2,918 rows × 19 columns with a data dictionary. The study model is an attention-based LSTM with hyperparameters tuned by the Honey Badger Algorithm.
decisions
  • Monthly, not weekly. Monthly was the finest resolution every source could support for all ten years. Weekly would have left gaps to fill with assumptions.
  • Checked completeness and consistency before any pre-modelling step, because each cleaning method makes its own assumption about the gaps.
result
MSE 43.7% lower than a standard LSTM and 22.2% lower than an attention-only model, per the published abstract. The model still underpredicts extreme spikes, and the paper reports that next to the results.

linear-git-skills

Two Claude Code skills that handle the branch-to-PR loop for teams using Linear's GitHub integration.

problem
Linear links a branch to an issue only if the branch name matches the one Linear would have generated. If the name is wrong, nothing gets linked and nothing warns you. You only notice later, when the board is out of date.
how
create-feature-branch looks up the issue, names the branch, cuts it from an up-to-date base and pushes with tracking. create-pr runs the project's checks, pushes, summarises the actual diff and opens the PR.
decisions
  • Uses Linear's own gitBranchName instead of re-implementing the slug, which could drift.
  • Read-only against Linear. With two-way sync, writing from both sides creates duplicate issues.
  • If a PR is already open, update its description instead of failing, so the body never describes an older diff.
safeguards
Refuses to branch over a dirty working tree and points to git stash pop --index. Never pipes a check it reports on. Logs use [OK] / [WARN] / [ERROR] so they stay readable in CI.

GitHub Skills exerciseGitHub Actions

Agentic workflow with a review gate

A scheduled agent that drafts content updates for a small Astro site and hands them over as a draft pull request.

how
Authored in Markdown with YAML frontmatter and compiled to update-github-info.lock.yml. It reads a notes file, the GitHub Blog and the Changelog, then edits site/content/github-info.md.
safeguards
  • Read-only token permissions (contents, pull-requests).
  • Network access limited to three allowlisted hosts.
  • Changes come out as a draft PR, never a push to main. When there's nothing worth publishing, it calls noop with a reason.
  • The model credential is stored as a repository secret, not in the file.
result
It ran and opened a [mona]-prefixed draft PR, which I merged.

EGACE status dashboard

An Excel report that shows where a scholarship batch stands across five stages: Enrolled, Graduated, Assessed, Certified, Employed.

problem
Programme staff needed each batch's status without opening the underlying trainee records or counting stages one by one.
how
The stage counts are lookups against the trainee records, so they update from one source instead of being counted by hand. Completion, pass and employment rates sit next to the counts, with a funnel bar chart and an employment-status breakdown.
result
One view per batch instead of five separate counts. It is a recurring report, not a one-off.
